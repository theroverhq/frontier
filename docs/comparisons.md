# Adding comparison pages

Each file in `src/lib/content/comparisons/` becomes a normal, statically generated
web page using `ComparisonPage.svelte`. The Markdown filename determines the resource ID. URLs use the vendor name without
`rover-vs-`: `rover-vs-splunk.md` creates `/resources/comparisons/splunk/`.
Splunk and Microsoft Sentinel retain their S3 keys; older page URLs redirect.

## Add a comparison

1. Create `src/lib/content/comparisons/rover-vs-vendor.md`:

```markdown
---
title: Rover vs. Vendor
competitor: Vendor
navLabel: Vendor
description: Compare Rover and Vendor for your security team.
pdfFile: Rover-vs-Vendor-Battlecard.pdf
images:
  dark: /assets/comparisons/vendor/page-dark.jpg
  light: /assets/comparisons/vendor/page-light.jpg
  og: /assets/comparisons/vendor/og.jpg
---

**Your opening statement.**

Your introduction.

## Historical investigations

Your comparison copy.

## At a glance

| Evaluation area | Rover               | Vendor               |
| --------------- | ------------------- | -------------------- |
| Architecture    | Rover capabilities. | Vendor capabilities. |
```

2. Add the three images beneath `static/assets/comparisons/vendor/`. Use
   1440 × 900 for page images and 1200 × 630 for OG images. SVG flags are unrelated;
   comparison images support JPG, PNG, and WebP. The dark image is used by the
   current dark page design; the light image is retained in the metadata.
3. Upload the PDF privately:

```sh
npm run upload:comparison -- rover-vs-vendor /absolute/path/to/Battlecard.pdf
```

The command reads the page's metadata, checks the AWS account and private bucket,
then uploads to `comparisons/rover-vs-vendor/Rover-vs-Vendor-Battlecard.pdf`.
An optional `pdfFolder` field changes the storage folder; migrated pages use it
to retain their original keys. Keep the PDF outside `static/` and the repository.

4. Copy the generated row into the **Resources** tab of the existing private
   Google Sheet. Columns are **resourceId, title, pdfUrl, pageUrl**. Update the row
   if that resource ID already exists; don't add duplicates. Use the upload
   command's tab-separated output or its CSV in `build-resources/`.
5. Run the checks and publish through the existing GitHub Pages workflow:

```sh
npm run test:comparisons
npm run test:leads
npm run test:downloads
npm run check
npm run build
```

Navigation, sitemap entries, page routes, SEO, contents links, image cache
versions, and browser download allowlists are generated automatically. No
per-comparison Svelte component, Google deployment, Lambda deployment, or IAM
policy change is needed after the one-time generic backend upgrade.

## Content behavior

The text before the first `##` heading is the introduction. Level-two headings
create sections and contents links. IDs are derived from heading text; optionally
use `## Your title {#stable-id}` to preserve an existing anchor. Duplicate IDs fail
build checks. Lower-level headings, lists, links, bold text, and Markdown tables
are supported. Raw HTML is omitted and unsafe URLs or PDF paths are rejected.

Use meaningful titles and descriptions. PDF filenames must use letters, numbers,
underscores, or hyphens and end in `.pdf`; folders use lowercase letters,
numbers, and hyphens. The upload source can have any local filename because it
is stored under `pdfFile`.

Run `npm run generate:comparisons` to refresh generated files explicitly. It also
runs before development, type checking, and production builds. Restart the dev
server after changing content metadata to refresh the generated registry.

Generated files are outputs, not sources:

- `src/lib/generated/comparisons.json`: public metadata used by navigation and forms.
- `src/lib/server/comparison-pages.json`: rendered content used only by page loading.
- `integrations/google-leads/Resources.csv`: rows for the private Sheet.
- `integrations/private-downloads/resources.json`: legacy signer compatibility data.

## One-time backend upgrade

AWS's existing signer is upgraded to accept a PDF key from the authenticated
Google backend. Its role reads only `comparisons/*` in the dedicated private
bucket. Older ID-only Splunk/Sentinel requests remain supported during migration.
The shared secret, endpoint, PDF objects, and five-minute lifetime stay the same.

For Google, open the refreshed local guide generated by `npm run setup:google-leads`:

1. Replace `Code.gs`, save, and run **saveLead** once as the owner.
2. Deploy a **New version** under the existing web app URL. Keep the existing
   Script Properties and the already-authorized external-request permission.
3. Ensure the Resources rows match `integrations/google-leads/Resources.csv`.
   Existing lead rows and notification/CC settings are preserved.
4. Publish the website and test both forms.

Future resource approval is read from the private Resources Sheet on every
submission. The visitor submits a resource ID, never an S3 key. Google validates
the row, page URL, and lead, saves it, then sends that row's key to AWS using the
server-only secret. The browser accepts only the expected object URL generated
from the page metadata. Keys outside the comparison prefix, path traversal,
arbitrary hosts, and non-PDF keys are rejected.
